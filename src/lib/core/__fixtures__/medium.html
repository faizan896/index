How We Cut Our Build Times in Half

Daniel Okonkwo

·

5 min read
·
Nov 14, 2023

--

Eighteen months ago a full run of our continuous integration pipeline took about forty minutes. Nobody had decided it should be that slow. It got there one reasonable change at a time: a new test suite here, an extra lint step there, a dependency that pulled in half of the internet. By the time we looked at it seriously, engineers were opening a pull request, going to lunch, and coming back to find out whether they had broken anything.

Six weeks of focused work brought it down to eighteen minutes. This post describes what we changed, in the order that it mattered. If you only read one section, read the first one, because measuring was worth more than everything else combined.

Measure before you optimise

Our first instinct was to buy bigger machines. Our second instinct, luckily, was to find out where the time actually went. We exported timing data for every step of every pipeline run over a month and loaded it into a notebook. The results surprised all of us. The test suites we suspected were fast. The slow part was everything around them: installing dependencies, restoring caches that were rarely valid, and building container images from scratch on every run.

Seeing the distribution changed the conversation. Instead of arguing about which tests to delete, we could point to a chart and agree that eleven of the forty minutes were spent downloading the same packages we had downloaded the day before.

Make the cache honest

We had a dependency cache, but its key included a timestamp that someone had added years earlier to work around a corrupted cache. The workaround meant the cache was invalidated every day, so most runs started cold. Replacing the timestamp with a hash of the lockfile meant the cache stayed valid until the dependencies actually changed. That single line saved nine minutes on a typical run.

We applied the same idea to container images. Base layers that change rarely now live in a registry and are pulled, not rebuilt. Only the thin layer containing our own code is built on each run. Docker’s layer caching does the rest, as long as the Dockerfile copies the lockfile before the source tree.

Run less, not just faster

Our repository holds four services and a shared library. Every change ran every test, even when it touched only a README. We introduced a small script that maps changed files to the packages that depend on them and runs only the affected suites. A full run still happens on the main branch after every merge, so nothing slips through, but most pull requests now run a fraction of the tests.

We were nervous about this change, so we ran both strategies side by side for two weeks and compared the results. The selective runs caught every failure that the full runs caught. That evidence made it easy to switch for good.

Split the slow suites

The remaining time was dominated by our end-to-end tests, which drive a real browser against a staging stack. They were already reliable, so we split them across four parallel workers, balancing the shards by historical duration rather than by file count. Wall-clock time for that stage fell from fourteen minutes to under five.

What did not help

Bigger runners helped a little, but far less than we expected, because most of the pipeline was waiting on the network rather than the processor. Rewriting the lint configuration saved forty seconds and cost two days of arguments. Neither was worth it.

The lesson we took away is unglamorous. Slow pipelines are rarely slow for one dramatic reason. They are slow because of small, sensible decisions that nobody revisits. Put the timings where everyone can see them, and revisit them every quarter.
